# retro (#92) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers-extended-cc:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** After a run (a session, a slice, a bug or an epic), a `retro` skill reads the run's transcripts through a script, shows one ranked list of setup changes at a checkpoint, gives each accepted one a home, and starts the next retro from what became of them.

**Architecture:** One new skill, `skills/retro/`, with `references/finding-areas.md` and one standard-library Python script, `skills/retro/scripts/retro_moments.py`. The script does everything that has one right answer: it filters transcripts into moments, redacts them, finds a run's window and sessions, checks roost drafts, and parses and renders `retro:` comments. Its tests are `scripts/retro-moments.test.py` and `scripts/retro-offers.test.py`, with synthetic fixtures in `scripts/fixtures/retro-moments/`, and they run in `pr-checks`. The model's judgment (areas, ranking, Checked or Hypothesis, matching a finding to an earlier one) is in the skill's prose and is tested by four eval cases.

**Tech Stack:** Python 3 standard library (`argparse`, `json`, `re`, `datetime`, `os`, `unittest`), `gh`, Markdown skills, GitHub Actions.

**Spec:** #92 and its stories #111 to #115, with their `evals:` comments; `docs/design/issue-92-retro.md` (decisions 1 to 9) and `docs/design/issue-92-build-guide.html` on `issue-92-retro-design` at `4d99a65`; the tech lead prompt `docs/design/issue-92-tech-lead-prompt.md`.

**Config:** this plan was written with roost's own config, `.roost/config.yml` (`team.name: roost`, one repo `roost`, `tracker.kind: github`, `tests.kind: evals`, `vcs.stacking: gh-stack`). `~/.claude/roost/config.yml` on this machine links to another team's config. That one isn't used here.

## Contracts (checklist 2)

No repo has a `contract`. The contracts are the script's command line and JSON, and the skill's output.

### `retro_moments.py` command line

`python3 <skill folder>/scripts/retro_moments.py <subcommand> …`. Every subcommand prints one JSON object on stdout. Exit **0** whatever it finds (missing sessions, unparseable records, a failed private-details check are all in the JSON); **2** for bad arguments (argparse); **1** for a failure of its own, with `{"error": "<type>: <message>"}` plus whatever it had.

| Subcommand | Slice | Arguments | Output |
|---|---|---|---|
| `moments` | 1 | `TRANSCRIPT…` `[--since ISO] [--until ISO] [--config FILE]…` `[--repo-of PATH=REPO]…` | Moments, totals, unparseable, redaction drops (below) |
| `redact` | 1 | `[--config FILE]…`, text on stdin | `{text, dropped: bool, reason}` |
| `window` | 2 | `--key KEY` and one of `--state FILE` / `--comments FILE` (both allowed: state first) | `{start, end, source: "state"\|"comments", reason}` |
| `sessions` | 2 | `--key KEY --since ISO --until ISO --repo NAME=WORKDIR…` `[--projects DIR]` (default `~/.claude/projects`) | `{orchestrators: [...], repos: [{repo, sessions: [...], found: bool, reason}], ignored: [...]}` |
| `last-turn` | 2 | `--workdir DIR --msg-id ID…` `[--projects DIR]` | `{session, path, last_active, text, found: bool, reason}` |
| `roost-draft` | 3 | `--config FILE…`, draft Markdown on stdin | `{text, names: {from: to}, check: {passed, matches: [{entry, key}]}}` |
| `follow-ups` | 4 | `--comments FILE --states FILE` | `{first_retro, previous, items, history}` |
| `render-comment` | 4 | findings JSON on stdin | `{text}` |

`--config` takes the team config and then each override file (`roost-config`'s order). The script reads them as text (no YAML parser in the standard library; see Hard parts).

### `follow-ups` input and output

`--comments`: `[{"ticket": "PROJ-2789", "url": "…", "created": "ISO", "body": "retro: …"}]` (every `retro:` comment the tracker search returned, any order). `--states`: `{"PROJ-2801": {"state": "closed", "reason": "completed", "closed": "ISO"}, "PROJ-2802": {"state": "open"}}`, GitHub's `state`/`stateReason` or Jira's status category mapped by the skill to `open`/`closed` with `completed`/`not_planned`.

  "first_retro": false,
  "previous": {"ticket": "PROJ-2789", "date": "2026-03-04", "run": "PROJ-2789", "url": "…"},

    {"area": "Automated checks", "finding": "…", "destination": "acme-api lint rule", "link": "PROJ-2801", "state": "done", "evidence": "PROJ-2801 closed as completed 2026-03-06"},

`state` is `done` (closed as completed), `still open`, `dropped` (closed not planned, with the reason if the ticket gives one) or `unknown` (no ticket to read). `history` is every earlier retro's titles, oldest first, for the model's recurrence matching (not matched in the script).

### The `retro:` comment (fixed shape, decision 6)

```markdown
retro: 2026-03-04, PROJ-2789

| Area | Finding | Destination |
|---|---|---|
| Automated checks | `moment` imported despite the team using date-fns | acme-api lint rule: PROJ-2801 |
| Review rules | Unpaged list endpoints pass review (recurred: 2 runs) | config edit, for the user |

Rejected: "Review passed a list endpoint with no page size"; "14 searches to find the OpenAPI build"
```

The first line is `retro: <YYYY-MM-DD>, <run key>`. A destination is `<where>: <link>`, or `config edit, for the user`. No rejected findings: the line is `Rejected: none`. This matches the shape in `retro-recurring-ranks-up`'s prompt, so the eval and the parser agree.

### The checkpoint list (the skill's output)

| # | Severity | Area | Finding | Evidence | What skipping costs | Recommendation | Where |
|---|---|---|---|---|---|---|---|

- **Severity:** High, Medium, Low (decision 4), plus "recurred: N runs" when it applies.
- **Recommendation:** starts `Checked:` with the evidence, or `Hypothesis:` with the check, who can run it (a repo session, or only the user) and how long it takes against what the problem costs.
- **Where:** `Team config` (key), a repo name, or `roost`.
- Ends with: "Decide each by number: yes, no, or for a hypothesis, check now / ticket the check / skip."

### The roost draft (decision 8)

A bug: `.github/ISSUE_TEMPLATE/bug_report.yml`'s fields, in order: **Skill**, **What happened**, **Steps to reproduce**, **roost version**, **Coding agent and version**. Or, for a missing capability, an epic with roost's epic sections and a **Real-World Failure Case Study** (Date, What happened, What the user experienced, What should have happened, Root cause), as #92 has. The title is a Conventional-free sentence; the label `bug` or `epic`.
